# Testprotokoll FW-DS-03 – Hook blockiert Secrets in der Werkzeugeingabe

| Feld | Inhalt |
|---|---|
| Test-ID | `FW-DS-03` (Basis) |
| Framework-Version | 0.11.0 |
| Datum | 2026-09-10 |
| Prüfmethode | skript |
| Prüfgegenstand | `leitwerk-core/tests/scripts/hook-check-secrets.py` |

## Verfahren

Das Hook-Skript liest die Werkzeugeingabe als JSON von der Standardeingabe und blockiert mit
Exit-Code 2. Geprüft wurden zehn synthetische Eingaben: sechs mit Secret-Mustern, die
blockiert werden müssen, und vier ohne, die durchgelassen werden müssen. Alle Werte sind
erfunden; keiner stammt aus einer realen Quelle.

```text
python leitwerk-core/tests/scripts/hook-check-secrets.py < <Eingabe>
```

## Ergebnis

| # | Werkzeugeingabe (synthetisch) | Erwartet | Ergebnis |
|---|---|---|---|
| 1 | Inhalt beginnt mit der PEM-Kopfzeile eines privaten Schlüssels | Exit 2 | Exit 2 |
| 2 | Befehl mit `Authorization: Bearer <32 Zeichen>` | Exit 2 | Exit 2 |
| 3 | Inhalt `db.password = <synthetischer Wert, 11 Zeichen>` | Exit 2 | Exit 2 |
| 4 | Befehl mit `postgres://<nutzer>:<wort>@datenbank/biv` | Exit 2 | Exit 2 |
| 5 | Inhalt mit `AKIA…` (16 Folgezeichen) | Exit 2 | Exit 2 |
| 6 | Inhalt mit dreiteiligem JWT | Exit 2 | Exit 2 |
| 7 | Prosa: „Das Passwort gehoert nicht in den Quelltext." | Exit 0 | Exit 0 |
| 8 | `token = ab` (Wert unter der Längenschwelle) | Exit 0 | Exit 0 |
| 9 | `password=<TBD: aus dem Tresor>` | Exit 0 | Exit 0 |
| 10 | Gewöhnlicher Quelltext ohne Muster | Exit 0 | Exit 0 |

**Zehn von zehn wie erwartet, null Fehlschläge.** Alle sechs Musterkategorien des Skripts
sind abgedeckt.

Die Tabelle nennt die Kategorien und nicht die Muster: Die tatsächlich verwendeten Eingaben
enthalten vollständige Zeichenketten, und der Validator meldet dieses Protokoll sonst selbst.
Das ist kein Umweg, sondern die Probe aufs Exempel – die erste Fassung dieses Protokolls
wurde mit drei Fehlern zurückgewiesen, weil sie die Werte ausgeschrieben hatte
(`CR-2026-013`, Prüfung 6).

## Bekannter Falschalarm, bewusst in Kauf genommen

Fall 9 läuft nicht durch, weil das Skript den Platzhalter erkennt, sondern weil `<TBD:` unter
der Längenschwelle bleibt. Ein längerer Platzhalter wird blockiert:

```text
password=<SYNTHETISCHES-BEISPIEL>   → Exit 2
```

Das ist ein Falschalarm, und er bleibt bestehen. Die beiden Durchsetzungspunkte behandeln
Platzhalter absichtlich verschieden:

| | Hook | Validator |
|---|---|---|
| Prüft | eine laufende Werkzeugoperation | den versionierten Bestand |
| Kosten eines Falschalarms | eine blockierte Operation, die der Mensch anders formuliert | ein Fehler, der jeden Release-Lauf anhält |
| Platzhalter in spitzen Klammern | wird blockiert | ist ausgenommen |

Beim Hook ist die strengere Auslegung die sichere: Blockieren ist billig, Durchlassen nicht.
Beim Validator wäre sie es nicht – das Framework schreibt seine Beispiele durchgehend mit
Platzhaltern, und ein Fehler je Beispiel machte den Testfall unbrauchbar.

## Bekannte Grenzen

- Geprüft ist das Skript, nicht seine Auslösung durch einen KI-Client. Ob der Client den Hook
  mit diesem Eingabeschema aufruft und Exit-Code 2 als Blockade auswertet, bleibt Gegenstand
  von Roadmap AP2 (`FW-AK-02`).
- Der Hook läuft weiterhin **fail-open**: Eine nicht als JSON lesbare Eingabe wird
  durchgelassen, solange `FW_HOOK_FAIL_CLOSED=1` nicht gesetzt ist. Die Umstellung auf
  fail-closed steht in AP2 und setzt voraus, dass das Eingabeschema bestätigt ist.
- Die Muster erkennen Formen, keine Bedeutungen. Ein Secret ohne Zuweisungssyntax und ohne
  bekanntes Präfix – eine nackte Zeichenkette – wird nicht erkannt. Dagegen tragen die
  Leseverbote der Berechtigungsdatei (`.env`, `**/*.pem`, `**/secrets/**`).
